# 技术架构

## 总体组织

采用模块化后端，Web 和小程序共用业务 API。解析、模型分析、图同步、清理和导出通过后台任务执行。首版不按模块拆分微服务，不另建数仓。

Web 使用 Vue 3 + TypeScript，小程序采用微信原生 TypeScript + Skyline + glass-easel，公众号复用响应式 H5。业务 API 使用 Django 5.2 LTS + DRF，Worker 使用独立 Celery 进程，Redis 承担消息代理。运行版本、依赖锁文件与启动方式见[开发说明](development.md)。

| 部分 | 职责 |
| --- | --- |
| Web | 原文阅读、编辑、审阅、版本比较和导出 |
| 微信小程序 | 资料收集、证据查看、短笔记和待办 |
| 业务 API | 身份、项目权限、数据版本、作者决定和任务入口 |
| Worker | 解析、AI 分析、文档导出及清理 |
| Pi 执行适配 | 组织受限的模型与工具调用，向任务服务上报事件 |
| PostgreSQL + pgvector | 业务事实、事务、任务、版本及资料检索 |
| Neo4j | 依据关系的查询投影，支持路径和影响分析 |
| SeaweedFS S3 | 原件、预览、模板和导出文件 |

## 模型执行

Pi 只接入项目需要的业务工具：检索材料、读取证据、保存摘记、提出诊断和修改建议。不开放任意命令、服务器文件访问或不受限制的网络请求。

业务后端决定工具的用户、项目和版本范围。文献内容按数据处理，不能改变系统规则。开始任务、调用工具和发布结果时复核当前授权；取消或撤权后不再发起新调用，迟到结果不发布。

模型没有“代作者接受建议”“发布正文”或“修改权限”的工具。结构化输出通过校验后，进入待核对区。

向量编码由后端调用管理员配置的外部嵌入 API，不部署本地向量模型。PostgreSQL pgvector 保存向量并执行授权项目内检索；API 地址、模型、维度或管理员标记版本改变后，旧索引不可继续混用，须重建。资料片段和查询文本会发送给该供应商，关键词检索不调用模型。

## 三条关键写入路径

**文件上传**：先登记上传意图，再写入对象存储并校验，最后发布业务引用。对象成功而数据库失败时进入对账，不能把不完整记录标为可用。

**作者采纳**：提交建议 ID、原稿版本和幂等键。服务端检查权限、规则、当前原稿与证据状态，再在同一事务中保存新正文、引用、作者决定和事件记录。

**关系同步**：业务数据与 outbox 事件在 PostgreSQL 一起提交，Worker 将事件投影到 Neo4j。消费同时检查事件 ID 和业务版本，防止重复和乱序恢复已撤回关系。

## 后台任务

任务保存输入快照、类型、状态、尝试次数、租约、错误和输出引用。任务失败与业务取消分开处理；只重试失败步骤，不重复发布已完成结果。

跨存储操作不假定存在统一事务。使用可重试步骤、状态记录和对账完成恢复，界面显示真实进度。

## 访问与数据保护

下载经过项目授权，短期链接使用明确的有效期；不承诺撤回已下载文件。模型请求只发送任务所需片段，日志脱敏，不记录密钥。

删除先阻断业务访问，再处理原件、解析片段、向量、图关系和相关产物。共享对象先检查其他引用；备份保留范围和清理时限单独说明。

## 部署

开发与演示环境隔离，存储使用独立数据卷。配置从环境变量读取，示例不包含凭据。初期单机部署，先验证恢复和关键流程，再根据实际负载考虑拆分。
